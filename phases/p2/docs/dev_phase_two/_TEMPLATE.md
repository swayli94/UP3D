# <一句话标题：这一轮做了什么>

轮次文件名：`yyyymmdd-hhmm-<name>.md`
阶段 / 门：`S<n>` / `GS<n>.<m>`（若是不属于任何门的工作，写"无门（工程/调查）"）
提交：`<commit hash 或 分支名>`

---

## 1. 目的

这一轮要回答的**一个**问题，或要达到的**一个**门。
写清楚：**什么结果算失败**（预先写下，不允许事后放宽）。

如果这一轮开一个新阶段，在这里写下该阶段的 **kill criterion**。

## 2. 改了什么

- `path/to/file.py` — 改动要点（一行一条）
- 新增旋钮（如果有）：名字、默认值、**删除条件**（roadmap 原则 4）
- 明确写：哪些是默认行为的改变，哪些是新增可选路径

## 3. 怎么测的

- 命令（可复制粘贴，含线程环境变量）
- 用的算例 / 网格 / 工况
- 参考值来自哪里（**外部真值** or 仅防漂移的历史值——必须区分，roadmap 原则 1）

## 4. 结果

带数字的表格。至少包含：

| 量 | 改动前 | 改动后 | 门 | 判定 |
|---|---|---|---|---|
|  |  |  |  |  |

产物路径：`results/...`（每个数字都要能查到对应文件）

必报两项：
- **全套测试**：`N passed / N failed / N skipped / N xfailed`，墙钟，线程数
- **基线 A/B**：对 `bench/baseline_*.csv` 的差异（哪些量动了、动了多少）

## 5. 判定

**PASS / FAIL / RECORDED** —— 三选一，对着 §1 预先写下的标准。
FAIL 就写 FAIL，不改门。

一句话结论（会被抄进 `progress.md`）。

## 6. 下一步

- 下一轮打算做什么（一件事）
- 这一轮暴露出的、但**不在**这一轮修的问题（登记，不顺手改）
- 如果判定 FAIL：按 kill criterion 转向哪里
