### 4.3 ★★ 自伤与修复:出处列的两行环境写法

PNG 重渲染跑用两行形式写环境(`export PYTHONNOUSERSITE=1 && NUMBA_NUM_THREADS=16
OMP_NUM_THREADS=16 OPENBLAS_NUM_THREADS=16` 换行后再跑 pytest)—— **`&&` 后的
赋值是 shell 局部量,不进子进程** ⇒ 导出的 CSV 记 `n_threads=unset`。
**而这不是第一次**:第 34 轮 D06/D08 的 footer 重渲染用了同一写法,于是
**已提交的** D06/D08 CSV 从 `2fa1532` 起就带着 `n_threads=unset`(D05/D11/D12/D13
正确)。本轮 `git diff` 检查时抓住 ⇒ 导出腿以**正确 export** 重跑,
D06/D08 的 CSV 现在只动这一列(unset → 16,物理列逐位未动,已逐行核对)。
★★ 教训与本项目的在案条目同族:**「出处列必须读真源」** —— numba 线程数是
H30 已证明无关的旋钮(所以物理列无恙),而真正量答案的 `blas_threads` 列
**全程正确地是 1** —— 出处列设计在第三次使用时就开始抓自己的作者。
⇒ 纪律化:跑导出/证据腿的命令,环境变量一律 `export` 或同行前缀,
**不许 `&&` 后裸赋值**;本行已写进轮次文件,防第三次。
